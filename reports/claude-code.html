Claude Code 深度解析：
闭源的引擎，敞开的接口

Claude Code 的核心程序不开源，但它把「怎么扩展它、怎么驱动它」全摊在了明面上：插件、Hooks、子代理、Mods，还有一份 MIT 协议的 Agent SDK。这份报告沿着这两条公开的线，把它从外面拆到协议那一层。

先说边界

Claude Code 的 CLI 本体通过官方安装器以二进制形式分发，源码不公开。本文只拆公开仓库里的代码和配置，CLI 内部只描述它对外暴露的接口和可观察到的行为，不猜测实现细节。

01取样：它是什么，为什么值得拆

Claude Code 是 Anthropic 出的一款 agentic 编程工具：它能读你的代码库、改文件、跑命令、处理 git，入口有终端、IDE 插件、桌面 App 和 GitHub 上的 @claude。

想搞懂「一个 AI Agent 产品是怎么搭起来的」，它是很好的样本：模型、工具循环、权限、上下文和扩展机制都做成了成熟的产品。引擎看不到，但下面两个仓库把外围拆得很清楚：

仓库里面有什么规模
anthropics/claude-code13 个官方插件、4 个内置 Mod 的源码、Hooks / 企业配置 / 网关示例、完整 CHANGELOG、Issue 自动化脚本。不含 CLI 源码。1614 个文件，CHANGELOG 423 个版本条目
anthropics/claude-agent-sdk-python用 Python 驱动 Claude Code 的 SDK：启动 CLI 子进程、收发消息、注册工具和钩子。src/ 约 1.3 万行 Python

所以这份报告分两条线拆：扩展线（插件、Hooks、Mods 怎么改变它的行为）和驱动线（外部程序怎么通过 SDK 遥控它）。

02测绘：先看清全貌

把公开信息拼起来，Claude Code 大致是四层结构：多个入口共用一个闭源引擎，引擎外面是一圈用文本、JSON 和 TypeScript 写的扩展接口，最底下是分层的配置文件。

claude-code 仓库地图

03解剖：沿着两条线读到关键代码

驱动线：SDK 其实是在「遥控」一个 CLI 子进程

读完 SDK 最重要的发现是：它自己不调用模型，也不执行工具。它做的事是把 claude CLI 当成子进程启动，然后通过 stdin / stdout 上一行一个 JSON 和它对话。Agent 循环始终在 CLI 里跑。

第一步是找 CLI。_find_cli() 先找 pip 包里自带的 _bundled/claude，找不到再去 PATH 和几个常见安装目录里搜。所以 pip install claude-agent-sdk 之后不用另装 Claude Code。

第二步拼命令行。_build_command() 把 ClaudeAgentOptions 的每个字段翻译成一个 CLI 参数，固定的骨架是这样：

_internal/transport/subprocess_cli.py · _build_command()节选

cmd = [self._cli_path, "--output-format", "stream-json", "--verbose"]
# ... system_prompt / allowed_tools / model / permission_mode / mcp_servers ...
#     每个选项对应一个 --xxx 参数
cmd.extend(["--input-format", "stream-json"])

启动时它还会改环境变量：设 CLAUDE_CODE_ENTRYPOINT=sdk-py 告诉 CLI「是 Python SDK 在调用你」，并去掉 CLAUDECODE，免得 SDK 起的子进程误以为自己跑在另一个 Claude Code 里。

控制协议：同一条管道里的两种消息

stdin / stdout 这根管道里跑着两类 JSON：一类是普通对话消息（user、assistant、system、result…），另一类是控制消息，用 request_id 配对请求和响应。读循环 _read_messages() 按 type 字段分流：control_response 唤醒正在等结果的请求，control_request 交给处理函数，其余的进消息队列。

控制请求是双向的：

方向subtype干什么
SDK → CLIinitialize开场握手：把 Python 里注册的 Hook 换成编号（hook_0、hook_1…）告诉 CLI，再带上子代理定义
SDK → CLIinterrupt · set_model · set_permission_mode运行中打断、换模型、换权限模式
SDK → CLIrewind_files · mcp_status · mcp_toggle · stop_task · get_context_usage回滚文件、查看和开关 MCP 服务器、停后台任务、查上下文占用
CLI → SDKcan_use_tool「我要用这个工具，你批不批？」交给你的 can_use_tool 回调
CLI → SDKhook_callback「编号 hook_0 的事件触发了」，SDK 按编号找到 Python 函数执行
CLI → SDKmcp_message转发一条 JSON-RPC 给进程内的 MCP 工具服务器

以 Hook 为例，Python 函数并不会被「传进」CLI。initialize() 只发编号，真正触发时 CLI 再用编号回调回来：

_internal/query.py · initialize()节选

for callback in matcher.get("hooks", []):
    callback_id = f"hook_{self.next_callback_id}"
    self.next_callback_id += 1
    self.hook_callbacks[callback_id] = callback   # 函数留在 Python 这边
    callback_ids.append(callback_id)              # 只把编号发给 CLI

用 @tool 和 create_sdk_mcp_server() 定义的「进程内工具」也是同样的思路：传给 CLI 的配置是 {"type": "sdk"}，去掉了真正的 Python 对象。CLI 要调用工具时发 mcp_message，SDK 在本进程里执行再把结果送回去。

设计亮点

引擎只有一份（CLI），所有语言的 SDK 都只是「协议客户端」。这样 Python 版和 TypeScript 版 SDK 不用各自重写一遍 Agent 循环，能力天然一致。代价是每次调用都要起一个子进程。

扩展线：五种扩展点，一个打包格式

① 斜杠命令就是一个 Markdown 文件。frontmatter 声明允许用哪些工具，正文里的 !`命令` 会在发给模型之前先执行，把结果拼进提示词。官方 /commit 命令的开头：

plugins/commit-commands/commands/commit.md节选

---
allowed-tools: Bash(git add:*), Bash(git status:*), Bash(git commit:*)
description: Create a git commit
---
- Current git status: !`git status`
- Current git diff (staged and unstaged changes): !`git diff HEAD`

权限也写得很细：只放行 git add、git status、git commit 三类命令，模型在这个命令里没法顺手 git push。

② 子代理同样是 Markdown：frontmatter 写名字、什么时候该用它、能用哪些工具、用哪个模型，正文就是它的系统提示词。feature-dev 插件里的 code-explorer 只给了只读工具，模型指定为 sonnet，专门负责读代码、追调用链。

③ Hooks 是最有意思的一层：在会话的关键时刻跑你自己的脚本。事件信息以 JSON 写进脚本的 stdin，脚本用退出码或输出 JSON 来影响 Claude 的行为。官方示例的注释写得很直白：

脚本怎么结束效果
退出码 0放行
退出码 2拦下这次工具调用，把 stderr 的内容交给 Claude 看
其他非零退出码stderr 只给用户看，不给 Claude
stdout 输出 {"decision": "block", "reason": …}拦截，并附上原因（下面的实验就用这个）

仓库里的插件用到了这些事件：PreToolUse、PostToolUse、UserPromptSubmit、SessionStart、SessionEnd、Stop、SubagentStop、Notification、PreCompact。两个官方插件把 Hooks 玩出了花：

  • ralph-wiggum：在 Stop 事件上挂脚本。Claude 想结束时，脚本输出 "decision": "block"，并把原始任务当作 reason 塞回去，于是 Claude 会拿同一个任务一轮轮继续干，直到说出约定的「完成暗号」或达到最大轮数。一个 Hook 就把单次对话变成了自动迭代循环。
  • security-guidance：同时挂了四个事件。编辑文件后用正则检查约 25 种危险写法；每轮结束把 diff 交给模型做安全审查；匹配到 Bash(git commit:*) 时再在后台用 Agent SDK 起一个审查代理，读相关文件追数据流，发现问题就用 asyncRewake 把 Claude 叫回来处理。

④ Skills 与 MCP：Skill 是一份按需加载的说明书（SKILL.md），MCP 服务器给 Claude 接入外部工具，插件里放一个 .mcp.json 就能带上。

⑤ Plugin 把上面这些打成一个目录：.claude-plugin/plugin.json 写元数据，旁边按需放 commands/、agents/、skills/、hooks/、.mcp.json，通过市场用 /plugin 安装。

新动向：Mods，把内置功能也做成插件

mods/ 是仓库里最新、也最值得关注的部分。按 README 的说法，Mod 是一种「行为写在 hooks 模块里」的插件：一个 register(on) 入口，用 on('事件', ($, e, next) => …) 挂到引擎的事件上，写法很像 Web 框架的中间件。这里放的四个 Mod 是随 Claude Code 一起发布的内置功能的源码：

  • diff：/diff 面板，在对话旁边按文件显示未提交的改动
  • agents-md：让 AGENTS.md 也能当项目说明使用
  • telemetry：内置插件的统计上报通道，在关闭统计的环境里什么都不发
  • sec-default：在企业托管环境下，防止用户自装的插件改动组织的策略

它们用 TypeScript 写，对照 types/claude-code.d.ts（1.3 万行声明）做类型检查，还能用 claude plugin test 跑单元测试。声明文件开头标着 EARLY ACCESS，接口可能随版本变化。

值得注意

当官方把 diff 面板这种核心功能也用插件接口来写，说明这套接口已经强到足以承载产品本身。对开发者来说，这意味着第三方插件理论上能做到和内置功能一样深的定制。

04复现：两个本地实验

实验环境

Windows 11，本机全局安装的 Claude Code 2.0.8（比研究版本旧，但下面用到的协议和 Hook 接口一致），未登录。两个实验都不需要真的调用模型，花费 $0。

实验一：亲眼看看 stream-json 消息流

SDK 解析的就是 CLI 在 --output-format stream-json 下吐出的东西。直接在终端跑一次：

claude -p "用一句话打个招呼" --model haiku --output-format stream-json --verbose

输出是三行 JSON，正好对应 SDK 里的三种消息类型：

第几行type / subtype看到了什么
1system / init会话开场信息：模型、权限模式（default）、可用工具列表（35 个，从 Task、Bash 到 WebSearch）、MCP 服务器、斜杠命令、session_id
2assistant因为没登录，这条是 CLI 合成的回复，model 字段写着 <synthetic>，内容提示 Invalid API key · Please run /login
3result / success收尾统计：is_error: true、num_turns: 1、耗时 132 ms、total_cost_usd: 0、token 用量全为 0

注意第 3 行：subtype 是 success，但 is_error 是 true。「CLI 正常跑完」和「这次回答出错了」是两个独立的标志，自己写解析代码时要同时检查两个字段。

实验二：用一个 Hook 拦下含密码的提示词

UserPromptSubmit 在提示词发给模型之前触发，所以不登录也能完整观察。写一个 Python 脚本：

guard.py完整代码

import json, sys

data = json.loads(sys.stdin.buffer.read().decode("utf-8"))   # 事件以 JSON 写进 stdin
with open("hook-input.json", "w", encoding="utf-8") as f:     # 存下来看看长什么样
    json.dump(data, f, ensure_ascii=False, indent=2)

if "密码" in data.get("prompt", ""):
    out = {"decision": "block", "reason": "猪猪研究所规定：提示词里不许出现密码"}
    sys.stdout.buffer.write(json.dumps(out, ensure_ascii=False).encode("utf-8"))

settings.json

{
  "hooks": {
    "UserPromptSubmit": [
      { "hooks": [{ "type": "command", "command": "python guard.py" }] }
    ]
  }
}
claude -p "我的数据库密码是 123456，帮我记一下" --settings settings.json --output-format stream-json --verbose

结果：消息流里只剩 system/init 和 result 两行，没有 assistant，num_turns: 0。提示词根本没送到模型那里。脚本存下的事件长这样（路径已省略）：

hook-input.json

{
  "session_id": "d8b29c59-…",
  "transcript_path": "C:\\Users\\…\\.claude\\projects\\…\\d8b29c59-….jsonl",
  "cwd": "…\\exp2",
  "permission_mode": "default",
  "hook_event_name": "UserPromptSubmit",
  "prompt": "我的数据库密码是 123456，帮我记一下"
}

可以看到 Hook 拿到的上下文很全：会话 ID、完整对话记录文件的路径、工作目录、权限模式。ralph-wiggum 正是靠 transcript_path 去读 Claude 的上一条回复，判断有没有说出「完成暗号」。

踩坑记录

第一版脚本用的是 json.load(sys.stdin)，在 Windows 上 Hook 静默失败：hook-input.json 是空文件，提示词照常发了出去。原因是 Windows 下 Python 默认按 GBK 读 stdin，而 Claude Code 写进来的是 UTF-8，中文一解码就抛异常。改成从 sys.stdin.buffer 读原始字节再按 UTF-8 解码就好了。Hook 脚本崩溃不会阻止提示词发出，写安全类 Hook 时一定要先测通。

进阶：用 SDK 把这两件事串起来（未在本机运行）

下面这段把「自定义工具」和「权限回调」放进同一个 SDK 程序，结构取自 SDK 的 README。它需要登录或 API Key 才能真正对话，本次没有运行，仅供对照上面的协议阅读：

import anyio
from claude_agent_sdk import (ClaudeAgentOptions, ClaudeSDKClient, PermissionResultAllow,
                              PermissionResultDeny, create_sdk_mcp_server, tool)

@tool("oink", "让小猪叫几声", {"times": int})
async def oink(args):                                   # 由 mcp_message 回调触发，在本进程执行
    return {"content": [{"type": "text", "text": "哼" * args["times"]}]}

async def gate(tool_name, tool_input, context):         # 由 can_use_tool 回调触发
    if tool_name == "Bash":
        return PermissionResultDeny(message="研究所里不许跑命令")
    return PermissionResultAllow()

options = ClaudeAgentOptions(
    mcp_servers={"pig": create_sdk_mcp_server(name="pig", tools=[oink])},
    can_use_tool=gate,
)

async def main():
    async with ClaudeSDKClient(options=options) as client:
        await client.query("调用 oink 工具叫 3 声")
        async for msg in client.receive_response():
            print(msg)

anyio.run(main)

05结论

ONE-LINER

Claude Code 是一个闭源的 Agent 引擎，外面包着一圈完全公开、用文本和 JSON 就能写的扩展接口；Agent SDK 不是另一个 Agent，而是用子进程加 JSON 行协议遥控这个引擎的客户端。

适合谁

  • 想用几行 Markdown 或一个小脚本，就把团队规范、安全检查塞进 AI 编程流程的人
  • 想在自己的后端、CI 里复用一个成熟 Agent 循环，而不是从零手写的人（用 SDK）
  • 想学习 Agent 产品怎么设计权限、钩子、插件体系的人

什么时候不该用

  • 必须能审计、修改引擎本身源码的场景：核心是闭源的
  • 想换成非 Claude 模型：可以走 Bedrock、Vertex 或网关，但模型仍是 Claude
  • 对每次调用的延迟极其敏感：SDK 每个会话都要起一个 CLI 子进程

猪猪的三条收获

  1. 扩展接口用最朴素的格式。命令和子代理是 Markdown，Hook 是读 stdin、写 stdout 的任意脚本。门槛低到几乎不用学，这是它插件生态能长起来的原因。
  2. 一个引擎，多种客户端。把 Agent 循环留在一处，SDK 只做协议翻译，多语言版本自然保持一致。自己做 Agent 产品时可以借鉴这种分层。
  3. Hook 要防「静默失败」。脚本崩了，请求照样会放行。凡是用来拦东西的 Hook，都要先用真实输入测一遍。
