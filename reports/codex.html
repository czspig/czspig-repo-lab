Report No.006 · AI Agent

Codex CLI 解析：
规则之外，再加一个笼子

Codex CLI 是 OpenAI 开源的本地编程 Agent。前几篇讲的权限系统，本质都是「执行前先问一问」；Codex 多做了一层：就算命令被放行了，也要关在操作系统级的沙箱里跑。这一篇只拆它的安全链路：命令规则、危险命令识别、沙箱和 AI 审批员。

01取样：它是什么，为什么值得拆

Codex CLI 是 OpenAI 的编程 Agent，在本地电脑上运行；同一个家族还有 IDE 插件、桌面 App（codex app）和云端的 Codex Web。核心代码在 codex-rs/，是一个用 Rust 写的大型 workspace：

样本卡
规模9515 个文件；最大的几个 crate 是终端界面 tui、app-server-protocol 和 core
安全相关 crateexecpolicy（命令规则）、shell-command（命令解析与危险识别）、sandboxing、linux-sandbox、windows-sandbox-rs、network-proxy，以及 core 里的 guardian
安装官方脚本、npm install -g @openai/codex、Homebrew，或直接下载 GitHub Release 里的二进制

研究所已经拆过 Claude Code、OpenCode、DeepSeek Harness，Codex 是主流编程 Agent 里的最后一块拼图。而且它的安全设计层次最多，正好单独拿出来讲。

02测绘：一条命令要过几道关

把读到的代码串起来，模型想执行一条 Shell 命令时，大致会经过下面这条链：

第三方文章把 Codex 的安全模型概括为「两根轴」：一根是审批策略（什么时候问人），一根是沙箱模式（命令跑起来能碰什么，比如只读、只能写工作区、完全放开），两者互相独立、可以分别设置。代码结构也印证了这一点：规则和审批在 core/exec_policy.rs，沙箱在单独的 crate 里。

03解剖：读到关键代码

命令规则：多条命中，取最严的那条

execpolicy 用 Starlark（一种长得像 Python 的配置语言）写规则，目前只有「前缀规则」一种：

codex-rs/execpolicy/examples/example.codexpolicy节选

prefix_rule(
    pattern = ["git", "reset", "--hard"],
    decision = "forbidden",
    justification = "destructive operation",
    match = [["git", "reset", "--hard"]],
    not_match = [["git", "reset", "--keep"], "git reset --merge"],
)

三个值得注意的设计：

  1. 取最严。一条命令可能同时命中好几条规则，最终结论取最严的一个：forbidden > prompt > allow。实现非常省事：Rust 的枚举按声明顺序自动可比较，取最大值就行。

    codex-rs/execpolicy/src/decision.rs节选，注释为意译

    #[derive(Clone, Copy, Debug, Eq, PartialEq, Ord, PartialOrd)]
pub enum Decision {
    Allow,      /// 直接放行
    Prompt,     /// 需要用户批准；approval_policy="never" 时直接拒绝
    Forbidden,  /// 不再考虑，直接拦下
}
  2. 规则自带单元测试。match 和 not_match 里写的示例会在加载规则时逐个校验，规则写错了，Codex 启动时就会报出来，而不是等到某次误放行才发现。
  3. 拒绝要给出路。README 建议在 forbidden 的 justification 里写上替代方案，比如「请用 jj 代替 git」，这段话会出现在给模型的拒绝信息里，模型能直接换条路走。

另外还有 host_executable：可以规定 git 只认 /usr/bin/git 等几个绝对路径，防止有人在别处放一个同名程序来蹭 git 的放行规则。

组合命令拆开逐段判

模型很喜欢写 a && b | c 这样的组合命令。exec_policy.rs 会先把它拆成几段，每段单独判断，再取最严。对 allow 的处理尤其谨慎：

codex-rs/core/src/exec_policy.rs节选

Decision::Allow => ExecApprovalRequirement::Skip {
    // Bypass sandbox only when every parsed command segment is
    // explicitly allowed by execpolicy.
    bypass_sandbox: commands.iter().all(|command| { /* 每一段都被规则明确放行 */ }),
    ...
}

也就是说，「不用审批」和「不进沙箱」是两回事：只有每一段都被规则明确放行（而不是靠启发式猜测为安全）才能跳过沙箱。用户点「以后都允许」时，Codex 会顺手提议往规则里加一条 allow 前缀规则，把一次性的批准变成可审查的规则。

危险命令识别：认真，但也承认极限

没有规则覆盖的命令，交给 shell-command 里的启发式判断。以最典型的强制删除为例，它会：

  • 剥掉外层包装：sudo、env A=1、trap '...' EXIT、bash -c '...'，看里面真正要跑的是什么
  • 解析 Shell 脚本，管道、if、for 循环、$( ) 里的每一条字面命令都要检查
  • 识别 rm -rf、rm -r -f、rm --force 等各种写法；-- 之后的参数不当作选项
  • 包装层数超过 8 层，直接当作危险处理（宁可错拦）
  • Windows 下另有一套 PowerShell 的识别规则

有意思的是它的测试用例，明确列出了认不出来的情况：

is_dangerous_command.rs · non_forced_or_non_literal_rm_is_not_dangerous节选

vec_str(&["bash", "-lc", "cmd=rm; $cmd -rf /tmp/example"]),   // 命令名放在变量里，静态分析看不出来

命令名到运行时才确定，任何静态检查都无能为力。这正是 Codex 还需要沙箱的原因：规则和启发式都可能漏，最后一道防线不能依赖「猜对」。

操作系统沙箱：从「全部禁止」开始

macOS 用系统自带的 Seatbelt，策略文件开头就是一句「默认全部拒绝」，注释写明参考了 Chrome 浏览器的沙箱策略：

codex-rs/sandboxing/src/seatbelt_base_policy.sbpl节选

; inspired by Chrome's sandbox policy
; start with closed-by-default
(deny default)

; child processes inherit the policy of their parent
(allow process-exec)
(allow process-fork)

Linux 用 bubblewrap 加 seccomp，linux-sandbox/README.md 写得很具体：

  • 整个文件系统默认只读挂载（--ro-bind / /），只有允许写的目录再单独挂成可写
  • 可写目录里的 .git 和 .codex 会被重新设回只读：Agent 能改代码，但改不了 git 历史和自己的配置
  • 限制网络时，用 seccomp 直接拦截网络相关的系统调用；并且始终禁用 io_uring，防止有人借它绕过对网络的限制
  • 多层路径规则按「越具体越优先」叠加：/repo 可写、/repo/a 禁止、/repo/a/b 又可写，三者都能正确生效
  • WSL1 无法创建所需的用户命名空间，所以不支持，直接拒绝在沙箱里跑命令，而不是悄悄不设防

Windows 有单独的 windows-sandbox-rs crate，本文没有展开阅读。

Guardian：让另一个 AI 来审批

每次都问人很烦，全部放行又不安全。Codex 的折中是 Guardian：一个独立的审查代理，夹在「Agent 想执行」和「真正执行」之间。源码注释称它为「隔离的同步审查者」，并且写了一条底线：

codex-rs/core/src/guardian/decision.rs原文

/// `None` requests the existing user flow. No contributor is never an implicit allow.

意思是：审查没给出结论时，退回到问用户的流程，绝不默认放行。据第三方文章介绍，Guardian 会把低风险操作自动批准，高风险的仍然交给人，并继承当前会话的沙箱和网络设置；它目前是实验性、默认关闭的功能，各文章给出的配置项名称也不一致，使用前请以官方文档为准。

04复现：把规则引擎搬进 Python

Starlark 的语法基本是 Python 的子集，所以官方示例规则文件可以原样交给 Python 执行，只要先定义好 prefix_rule 函数。我写了一个 40 行左右的移植：前缀匹配、取最严、加载时自检、组合命令拆分。

execpolicy_lite.py核心逻辑

ORDER = {"allow": 0, "prompt": 1, "forbidden": 2}

def prefix_rule(pattern, decision="allow", justification=None, match=(), not_match=()):
    for ex in match:          # 规则自带的「单元测试」：加载时就校验
        assert matches(pattern, tokens(ex))
    for ex in not_match:
        assert not matches(pattern, tokens(ex))
    RULES.append((pattern, decision, justification))

def check(cmd, rules):
    hits = [d for p, d, _ in rules if matches(p, cmd)]
    return max(hits, key=ORDER.get) if hits else None   # 取最严；无匹配交给启发式

exec(open("example.codexpolicy").read(), {"prefix_rule": prefix_rule})

结果

官方示例里的 8 条规则全部加载成功，规则里写的示例也全部通过自检。逐条测试：

规则顺序的实验

同样两条规则：「git 一律允许」和「git push 禁止」，只调换先后顺序，再分别用 Codex 的「取最严」和 OpenCode 的「后者优先」判断 git push：

规则顺序Codex（取最严）OpenCode 式（后者优先）
先写宽的，后写严的forbiddenforbidden
先写严的，后写宽的forbiddenallow
发现

「后者优先」的好处是能写出「全部禁止，但示例文件放行」这种精细的例外（OpenCode 那篇的 .env.example 就是这么做的），代价是顺序写错就会意外放行。「取最严」不怕顺序，但没法用一条宽松规则覆盖严格规则，想开例外只能把严格规则写得更窄。两种语义没有绝对的对错，但换工具时一定要先弄清楚是哪一种。

最后再故意写一条错规则：pattern=["rm"] 却声明不应匹配 rm x。加载时直接报错，错规则进不了系统。

05结论

ONE-LINER

Codex 的安全设计是「多层都可能漏，所以层层设防」：规则取最严且自带测试，组合命令逐段判，危险命令尽力识别也坦白极限，最后无论如何都关进默认拒绝的系统沙箱，审批还能交给一个绝不默认放行的 AI 审查员。

适合谁

  • 在乎安全、希望 Agent 默认就被关在沙箱里的开发者
  • 需要把团队的命令规范写成可审查、可测试规则的团队
  • 想学习「纵深防御」怎么落到 Agent 上的人：这是目前读过最完整的一套

什么时候不该用

  • 想用别家模型又不想折腾：默认围绕 OpenAI 账号和模型，接其他服务商需要额外配置
  • 环境特殊：Linux 沙箱依赖用户命名空间，WSL1 等环境不支持
  • 希望规则能「后写覆盖前写」：Codex 的取最严语义写不出这种例外

猪猪的三条收获

  1. 静态检查一定有漏洞，沙箱是兜底。cmd=rm; $cmd -rf 这种写法谁也拦不住，真正可靠的是「就算放行了，也碰不到不该碰的东西」。
  2. 规则也要有测试。把正反例写进规则本身、加载时就验，这个做法几乎可以照搬到任何配置系统。
  3. 权限语义要先读懂再写。「取最严」和「后者优先」看起来差不多，换个顺序结果就完全相反。
