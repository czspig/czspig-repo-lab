Report No.007 · 本地模型

Ollama 解析：
模型在你电脑里是怎么「住」下来的

前几篇拆的都是模型外面那一圈（harness）。这一篇往下挖一层：一个大模型文件，是怎么被加载进显卡、对外提供接口、什么时候被请出内存的。研究对象是最流行的本地模型运行器 Ollama，实验就在我自己的电脑上跑。

01取样：它是什么，为什么值得拆

Ollama 让你用一条命令在自己电脑上跑开源大模型：ollama run 模型名，下载、加载、对话一气呵成；它同时在 127.0.0.1:11434 开一个 HTTP 服务，别的程序都能来调用。

样本卡
语言主体是 Go，研究所第一次拆 Go 项目
推理引擎固定版本的 llama.cpp 加一组兼容补丁（llama/）；苹果芯片上另有基于 MLX 的运行器（mlxrunner/）
接口自家 API，外加 OpenAI 兼容和 Anthropic 兼容接口
和本系列的关系官方文档里有 Claude Code、Codex、DeepSeek Harness 的接入页面，ollama launch claude 就能让 Claude Code 跑在本地模型上

研究所前面拆了 Claude Code、OpenCode、Codex、DeepSeek Harness，它们都能接到 Ollama 上。所以这篇想回答一个很实际的问题：拿本地模型跑编程 Agent，Ollama 这一层有哪些坑？

02测绘：先看清全貌

两个值得一提的工程选择：

  • 每个模型一个子进程。Go 写的服务负责排队、调度和接口；真正做矩阵运算的是单独的运行器进程。一个模型的运行器出问题，通常不会把整个服务一起拖垮。
  • llama.cpp 固定版本，升级要按清单验。llama/README.md 开头就提醒：升级 llama.cpp「影响的不只是编译」，还可能改变模型加载、显卡识别、调度器的输入和日志格式，后面附了一整份审查清单。依赖一个更新飞快的上游项目时，这种「固定版本 + 补丁 + 升级清单」的做法很稳。

03解剖：读到关键代码

调度器：装得下吗，请谁出去

每个请求先进队列，调度器 processPending 逐个处理：

  1. 这个模型已经加载了，而且参数（比如上下文长度）没变？直接复用。
  2. 没加载，并且已加载的模型数没超上限？算一下显存够不够，够就加载。上限默认是每块显卡 3 个，纯 CPU 时也是 3 个。
  3. 装不下？挑一个已加载的模型请出去，等它卸载完再试。
  4. 加载过程中内存溢出崩了？把其他模型全部卸掉，只再试一次；第二次还崩就直接报错，不无限重试。

「请谁出去」的规则在 findRunnerToUnload：先按保留时长从短到长排序，优先挑当前空闲的；都在忙，就等保留时长最短的那个。

这里有个小技巧：keep_alive: -1 表示「永远别卸载」，负数转成无符号整数后会变成一个巨大的数，排序时自然排在最后，于是「永久驻留」的模型最后才会被请出去，不需要额外写特殊判断。

keep_alive：模型在内存里留多久

每次请求完成后，模型会在内存里再留一段时间，下次请求就不用重新加载：

keep_alive效果
不设置默认留 5 分钟（可用环境变量 OLLAMA_KEEP_ALIVE 改全局默认）
"30m"、"45s" 等留指定时长；每次被使用都会重新计时
-1永远留着
0用完立刻卸载

请求里带的 keep_alive 会覆盖全局设置。编程 Agent 隔一会儿就会发请求，保留时间太短就会反复冷启动，下面的实验会看到冷启动有多慢。

上下文长度：最容易踩的坑

docs/context-length.mdx 写着，Ollama 按显存大小决定默认上下文长度：

显存默认上下文
小于 24 GiB4k
24 – 48 GiB32k
48 GiB 及以上256k

同一份文档又说，Agent、编程工具这类任务至少要 64k；Claude Code 和 Codex 的接入页面也都写了「64k 以上」。也就是说，大多数家用显卡的用户，什么都不改就让 Agent 接本地模型，拿到的只是 4k 的上下文：系统提示词加上工具定义可能就占满了（DeepSeek Harness 那篇提到，一个最简单的任务第一次请求就要约 1.3 万 token）。

代码里还有几条相关规则：设置的长度超过模型训练时的上限，会被截到上限（effectiveContext）；同时处理 N 个请求时，显存占用会按 N 倍增长；自动设置的上下文在加载时内存不够，调度器会自动调小再试（reduceAutoNumCtxForLoadOOM）。

「支持工具调用」是怎么判断的

OpenCode 只把声明了 tools 能力的本地模型当作能干活的 Agent 模型。这个能力标签是 Ollama 给的，对于 GGUF 模型，主要判断方式朴素得出人意料：

server/images.go原文

func chatTemplateHasToolSupport(chatTemplate string) bool {
	return strings.Contains(chatTemplate, "tools") || strings.Contains(chatTemplate, "tool_call")
}

也就是看模型自带的对话模板里有没有出现 tools 或 tool_call 这两个词。旁边另有一个更严格的检查 chatTemplateHasToolRoundTrip，要求模板能处理「工具调用 → 工具结果」的完整往返。字符串匹配简单高效，但也意味着：标了 tools，只说明模板「提到了」工具，不代表模型真能用好工具。

04复现：在我电脑上量一量

用 Python 标准库直接调本机 Ollama 的接口（绕过系统代理），模型是 granite4.1:3b（34 亿参数，Q4_K_M 量化）。流程：查版本和能力 → 先卸载确保冷启动 → 连续请求两次 → 看内存里的状态 → 用 keep_alive: 0 卸载。

probe.py核心片段

最后用 keep_alive: 0 再发一次，查询加载列表立刻变空，模型被卸载了。

发现

一，训练时支持 13 万 token 的模型，在我的电脑上只拿到 4096，说明这台机器被归进了「显存小于 24 GiB」那一档，和文档的默认规则一致。要拿它跑编程 Agent，必须先用 OLLAMA_CONTEXT_LENGTH 或接口参数调大，前提是显存装得下。二，冷启动比热启动慢了约 500 倍。除了加载模型的 25.7 秒，第一次读入提示词也花了 17.8 秒，而第二次只要 34 毫秒，多出来的时间应该是显卡第一次运行时的预热开销。对 Agent 来说，把 keep_alive 设长一点，几乎是最划算的优化。

05结论

ONE-LINER

Ollama 用一个 Go 写的调度器管理一群模型子进程：谁先进内存、谁被请出去、留多久，都有清楚的规则。拿它给编程 Agent 当后端时，真正要盯的是两个默认值：小显存下只有 4k 的上下文，以及 5 分钟就会过期的 keep_alive。

适合谁

  • 想在本地、离线、零调用费用地用开源模型的人
  • 需要数据不出本机的场景
  • 想给 Claude Code、Codex、OpenCode 找一个本地后端做实验的人

什么时候不该用

  • 显存不够又要长上下文：开到 64k 可能装不下，或者被迫部分放到 CPU 上，速度大幅下降
  • 对效果要求高的复杂编程任务：本地小模型和云端大模型差距仍然明显
  • 高并发服务：默认每个模型一次只处理 1 个请求，并发要调参数并付出成倍的显存

猪猪的三条收获

  1. 默认值决定了大多数人的体验。4k 上下文对聊天够用，对 Agent 不够；接本地模型前先看一眼 ollama ps 的 CONTEXT 列。
  2. 能力标签要打个问号。「支持 tools」只是模板里出现了这个词，模型实际用得好不好还得自己测。
  3. 依赖飞速更新的上游，要固定版本并配升级清单。Ollama 对 llama.cpp 的处理方式，放到任何项目里都适用。
