MCP 解析：
Agent 世界的通用插头，刚刚换了芯

研究所前七篇几乎每篇都绕不开 MCP（Model Context Protocol）：REA 是 MCP 服务器，Claude Code、Codex、OpenCode、DeepSeek Harness 都是 MCP 客户端。这一篇直接读协议规范本身，并且赶上了一次大改版：最新版 MCP 去掉了握手和会话，变成了「无状态」协议。最后用几十行 Python 手写一个迷你 MCP 服务器，把每条消息摆出来看。

01取样：它是什么，为什么值得拆

MCP 规定了「AI 应用」和「给 AI 提供能力的服务」之间怎么说话。有了它，一个工具服务写一次，就能被所有支持 MCP 的 Agent 使用；一个 Agent 支持一次 MCP，就能接上成千上万个现成的工具服务。

样本卡
底层格式JSON-RPC 2.0：一个请求带 id、method、params，回一个 result 或 error
传输方式stdio（本地子进程，标准输入输出里一行一条消息）和 Streamable HTTP（远程服务）
版本用日期命名：2024-11-05、2025-03-26、2025-06-18、2025-11-25、2026-07-28，另有 draft
仓库内容规范文档、用 TypeScript 写的数据定义（schema.ts，另生成 JSON Schema）、示例、改进提案（SEP）

它值得拆，一是因为它是整个系列的公共底座；二是因为刚发布的 2026-07-28 版做了好几处不兼容的大改，看规范怎么演进，比看某个实现更能理解设计取舍。

02测绘：先看清全貌

三类角色，两头能力

MCP 里有三类角色：宿主（Host，比如 Claude Code 这个应用）、客户端（宿主里负责连某个服务的那部分）、服务器（提供能力的一方，比如 REA）。能力分两头：

谁提供能力说明
服务器Tools 工具由模型自己决定调用的函数，最常用
Resources 资源可读取的数据，比如文件、数据库记录
Prompts 提示词预设的提示词模板，常以斜杠命令的形式出现
客户端Elicitation 征询服务器需要向用户要信息时，由客户端去问
Sampling 采样服务器借用客户端的模型生成内容（本版起已弃用）
Roots 根目录告诉服务器能访问哪些目录（本版起已弃用）

2026-07-28 版：从「先握手再说话」到「每句话都自报家门」

这一版 changelog 里的「重大改动」主要有这几条：

  • 去掉握手。initialize 和 notifications/initialized 都没了，每个请求都在 _meta 里自带协议版本、客户端能力和身份。
  • 去掉会话。HTTP 传输不再有 Mcp-Session-Id，工具列表也不再因连接而异。
  • 新增 server/discover。服务器必须实现，用来一次性告诉客户端自己支持哪些版本、有什么能力。
  • 新增「多轮请求」（MRTR）。服务器不能再主动向客户端发请求，改为「回一个需要补充信息的结果，等客户端带着答案重试」。
  • 所有结果都带 resultType。普通结果是 complete，需要补充信息的是 input_required。

03解剖：读到关键设计

为什么要「无状态」

MRTR 那一章的开头说得很直白：这样做是为了处理服务器向用户要信息的场景，同时不需要服务器实例之间共享存储，也不需要「会话粘连」的负载均衡。翻译成大白话：以前一个连接只能由一台服务器从头服务到尾，现在任何一个请求都能被任意一台服务器处理，远程 MCP 服务就能像普通网站一样横向扩容。

那需要跨调用记住东西怎么办？规范给的答案是显式的句柄：创建类的工具返回一个 ID，后续调用把它当普通参数传回来。规范举的例子是购物车：

server/tools.mdx · Stateful Tools节选

// → tools/call
{ "name": "create_basket", "arguments": {} }
// ← result
{ "structuredContent": { "basket_id": "bsk_a1b2c3" } }
// → tools/call
{ "name": "add_item", "arguments": { "basket_id": "bsk_a1b2c3", "sku": "..." } }

规范还提醒了句柄的几条设计原则：每次调用都要重新校验权限（句柄只是名字，不是通行证）；用不透明的随机 ID，别让人能猜出结构；在工具描述里写清楚多久过期，让模型自己判断；过期了要回一个模型看得懂的错误，好让它重新创建。

多轮请求（MRTR）：服务器不再「反问」

以前服务器处理请求时如果需要用户补充信息，会反过来给客户端发一个请求，这要求连接一直保持着。现在改成这样：

  1. 客户端发请求
  2. 服务器发现信息不够，回一个 resultType: "input_required"，里面的 inputRequests 写着要问什么，可以附一个只有服务器自己看得懂的 requestState
  3. 客户端去问用户（或者调用自己的模型），然后用新的请求 id 重发原请求，带上 inputResponses 和原样奉还的 requestState
  4. 服务器信息够了，返回最终结果

规范要求客户端不得解析、修改或猜测 requestState 的内容。状态从服务器内存里搬到了消息里，由客户端「代为保管」。

工具：描述、提示、两种错误

一个工具的定义包括名字、描述、输入的 JSON Schema、可选的输出 Schema，以及一组行为提示（annotations）。提示的默认值很有讲究：

提示含义不写时默认
readOnlyHint不修改环境false（当作会修改）
destructiveHint可能做破坏性修改true（当作会破坏）
idempotentHint重复调用效果相同false
openWorldHint会接触外部世界true

什么都不声明的工具，会被当成「会改东西、会搞破坏、会联网」的最危险那一类。这和 REA 那篇里「新工具一律先按不可信处理」是同一种思路，REA 的 212 个工具副作用审计，正是为了把这几个提示填准确。

但规范同时强调两点：

  • 提示不可信：除非服务器本身可信，客户端必须把这些提示当作不可信信息。服务器完全可以把一个删库工具标成「只读」。
  • 人要能说不：应当始终有一个人能拒绝工具调用；界面上要让用户知道暴露了哪些工具、什么时候被调用了。

错误也分两种，这个区分很为 Agent 着想：

类型例子怎么返回
协议错误工具不存在、请求格式不对JSON-RPC 的 error，模型通常修不了
工具执行错误参数值不合法、外部接口失败正常的 result 加 isError: true，错误内容会给模型看，让它自己调整重试

为 Agent 和缓存做的小优化

  • 工具列表顺序要固定。changelog 写明，服务器应当以确定的顺序返回工具，理由之一是提高大模型提示词缓存的命中率。这和 OpenCode 最后一步保留工具定义是同一个考虑。
  • 列表结果可缓存。tools/list 等结果必须带 ttlMs（多久内可以直接用缓存）和 cacheScope（能否被共享的中间层缓存）。
  • 做减法。ping、logging/setLevel 被删除；Roots、Sampling、Logging 三项能力被弃用，建议改用工具参数传目录、直接调用模型服务商的接口、日志写 stderr 或用 OpenTelemetry。

04复现：手写一个迷你 MCP 服务器

MCP 的 stdio 传输规则很简单：客户端把服务器当子进程启动，每行一条 JSON-RPC 消息，消息里不能有换行；日志只能写到 stderr，不能污染 stdout。所以只用 Python 标准库就能写一个服务器，约 60 行。它实现了 2026-07-28 版的这些部分：

  • server/discover
  • tools/list：两个工具，顺序固定，带 ttlMs 和 cacheScope
  • tools/call：add 做加法；greet 不知道你叫什么时，用 MRTR 反问
  • 每个请求都检查 _meta 里的协议版本，不支持就回 -32022

mini_server.py核心片段

if name == "greet":
    answer = params.get("inputResponses", {}).get("ask_name")
    if not answer:  # 多轮请求：反问客户端，自己什么都不记
        return {"result": {"resultType": "input_required",
                           "inputRequests": {"ask_name": {"method": "elicitation/create", ...}},
                           "requestState": "greet-v1"}}
    return {"result": ok({"content": [{"type": "text", "text": f"Oink! Hello, {answer['content']['name']}."}]})}

for line in sys.stdin:                        # 一行一条消息
    msg = json.loads(line)
    print(f"[server] {msg['method']}", file=sys.stderr)   # 日志只写 stderr
    sys.stdout.write(json.dumps({"jsonrpc": "2.0", "id": msg["id"], **handle(msg)}) + "\n")

再写一个客户端，启动服务器、依次发 7 个请求，把每条往返记下来。

结果

#客户端发了什么服务器回了什么
1server/discover支持的版本 ["2026-07-28"]、能力 tools、服务器身份、可缓存 1 小时
2tools/list两个工具，add 带 readOnlyHint: true；ttlMs: 300000
3tools/call add {a:2, b:40}content 里的文字「42」，加上结构化的 {"sum": 42}
4tools/call greetresultType: "input_required"，问「What should I call you?」
5用新 id 重发 greet，带上 inputResponses 和 requestState「Oink! Hello, Zhuzhu.」
6tools/call fly协议错误 -32602 Unknown tool: fly
7tools/list，但声称版本是 2025-11-25-32022，data 里列出支持的版本，让客户端换一个重试

第 4、5 步就是一次完整的多轮请求，服务器在两次请求之间没有保存任何东西，需要的上下文全在第二次请求里。服务器的 stderr 里只有一行行日志，stdout 始终是干净的 JSON。

发现

无状态的代价是每个请求都要自报家门。我量了一下：一个最简单的 tools/call，不带 _meta 是 110 字节，带上版本、客户端身份和能力之后是 335 字节，每个请求多出约 225 字节。这些字节只在客户端和服务器之间传，不会发给大模型，不消耗 token。用这点流量换来「任意实例都能处理任意请求」，对远程服务来说相当划算。

05结论

ONE-LINER

MCP 用最朴素的 JSON-RPC 把 Agent 和工具连起来；2026-07-28 版又往「朴素」走了一大步：去掉握手和会话，每个请求自带版本和能力，反问改成「回结果、等重试」，让 MCP 服务器能像普通网站一样无状态地扩容。

适合谁

  • 想给自家系统做一个能被各种 Agent 调用的工具服务的人
  • 在做 Agent、想一次接入大量现成工具的人
  • 想理解前几篇里 MCP 相关设计从哪来的人

需要注意

  • 新版有多处不兼容改动，旧客户端和新服务器混用时要靠 server/discover 和版本错误来协商
  • 工具提示（annotations）只是服务器的自我声明，不能代替客户端自己的权限和审批
  • 本文的玩具实现只覆盖一小部分规范，真要写服务器请用官方 SDK

猪猪的三条收获

  1. 状态放进消息里，服务就好扩容。购物车 ID、requestState 都是这个思路，自己写后端接口时同样适用。
  2. 危险的默认值比乐观的默认值安全。不写提示就当最危险的处理，逼着服务器作者主动声明。
  3. 区分「模型能修的错」和「模型修不了的错」。工具执行错误交给模型自我纠正，协议错误交给程序处理，这个分法值得在所有给 AI 用的接口里照搬。
