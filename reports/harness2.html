Report No.002 · Agent Harness

Harness² 深度解析：
不改模型，让 Agent 自己改装备

模型权重一动不动，只改围在它外面的那一圈东西：提示词、规则、记忆、技能、脚本。Google Research 的 Harness² 把这件事做成了一个自动循环：先试几种改法，看实际跑出来的差别，再合成更好的版本，最后把经验存给下一个任务。

01取样：它是什么，为什么值得拆

先认识一个词：harness，直译是「马具、挽具」。在 Agent 领域，它指模型外面那一整套让它能干活的东西：系统提示词、规则、记忆、工具说明、子代理、技能、脚本、插件。上一篇拆的 Claude Code，本质上就是一个做得很好的 harness。

Harness² 要解决的问题是：换一种没见过的任务时，怎么自动把 harness 调得更合适？它不训练模型，而是让一个「编辑」模型去改 harness 文件，然后用真实运行结果判断改得好不好。名字里的平方，指两层递归：

  • 任务级递归：在当前任务上「提议 → 探测 → 合成」，得到一个改进后的 harness。
  • Harness 级递归：每做完一个任务，就把采用的 harness 和学到的经验存进经验库，指导同领域的下一个任务。

README 里报告的效果：一步 Harness² 在 GLM-5 和 Gemini 3.5 Flash 上都比基础 harness 好，WorkBuddy-Bench 最多提升 11.5 分，JobBench 提升 4.5 分，法律基准 LAB 的部分通过率提升 11.8 个百分点。这些数字来自论文，本文没有复现。

样本卡
规模harness2/ 共 39 个 Python 文件约 1.27 万行：核心方法 core/ 约 5700 行，执行器适配 substrate/ 约 1000 行，三个基准的适配 benchmarks/ 约 4200 行
依赖核心零第三方依赖（dependencies = []），渲染和模型网桥是可选附加项
执行器OpenCode（默认）和 Codex：真正干活的 Agent 框架
运行环境官方只支持 Linux + Python 3.12（下面的实验会撞上这一点）

02测绘：先看清全貌

core/spec.py 开头的注释把整个项目的骨架说得很清楚：三条轴互不干扰。

轴是什么代码在哪
方法递归流程、提示词、选择、经验库：论文本身的贡献core/
执行器每次「跑一遍任务」用哪个 Agent 框架substrate/opencode.py、codex.py
基准任务从哪来、产物怎么读、最后怎么打分benchmarks/，实现 BenchmarkAdapter 协议

想接入自己的任务，只要实现 BenchmarkAdapter 的十几个方法：列出任务、执行一次、判断有没有交付、把运行轨迹转成文字、提供初始 harness……注释写的是「实现这些，整个方法就能工作；这里没有任何方法逻辑」。

八个可编辑组件

编辑模型能改的范围被严格限定为八类文件，同一个概念在两个执行器里落在不同路径上：

组件OpenCode 里的位置Codex 里的位置作用
系统提示词 · 规则 · 记忆 · 工具说明systemprompt.md、guardrails.md、LongTermMEMORY.md、tool_descriptions/tool_guidance.md合并在一个 AGENTS.md常驻上下文，每次运行都占 token
技能skills/<名字>/SKILL.md.agents/skills/…按需加载的操作手册
子代理sub_agents/<名字>/AGENT.md委派出去的专项工作
脚本scripts/<名字>.py重复、确定性的计算和检查
插件 / 钩子plugin/<名字>.ts.codex/hooks.json工具循环里的中间件

常驻文本有上限：OpenCode 2.4 万字符，Codex 8000 字符。代码里给的理由是「这里的每个 token 都在和 Agent 自己的输出预算抢位置」。

03解剖：读到关键代码

一次「提议 → 探测 → 合成」

提议这一步有个巧妙的分工：每轮固定派出两种编辑，各管一摊，互不越界。

INV：Agent 怎么干活

  • 只管流程、工具使用和收尾，不碰专业知识
  • 沿运行轨迹找到最早出错的地方，用最便宜的组件修
  • 重复的确定性操作写成 scripts/ 脚本；一次性小错不加代码

DOM：从业者知道什么

  • 只管产物结构、判断规则、领域检查
  • 有明确触发场景的知识优先写成技能，平时不占上下文
  • 两条硬规定：不许编造出处和标准；不把本任务的具体事实写进长期记忆

到合成这一步，合成者能看到所有候选的 harness、它们各自的运行结果和编辑说明，可以合并几份、整份采纳其中一份，或者保持原样。提示词特别强调了「下行风险」：只要哪个候选的运行什么都没交出来，就要明确标出来，默认视为不安全的改动。

并行和串行：预算一样，花法不同

--mode parallel 是「横向」：从同一份基础证据一次派出 2k 个候选，再独立做 k 次合成。--mode sequential 是「纵向」：每轮只派一对 INV / DOM，合成后的版本作为下一轮的起点，连续改 k 轮。

为了让两种模式能公平比较，core/ledger.py 把预算写成了一条恒等式，每跑完一个模式都要核对一遍：

harness2/core/ledger.py节选

def expected_rollouts(k: int) -> int:
    """R = 4k: k shared base + 2k candidates + k finals."""
    return 4 * int(k)


def expected_sessions(k: int) -> int:
    """P = 3k: k INV + k DOM + k compositions."""
    return 3 * int(k)

账对不上就直接抛 BudgetError。它还会先查有没有重复的标签，因为两个阶段写到同一个运行 ID 时，后一个会悄悄覆盖前一个，计数恰好也能凑对。

不偷看答案的四道防线

这类「自我改进」系统最容易出的问题，是编辑模型间接看到了评分标准，结果学会的是「讨好评分」而不是「把活干好」。Harness² 在代码层面设了好几道闸：

  1. 提示词里不许出现评测词汇。基准提供的任务描述只要包含 benchmark、evaluation、grader、rubric、score 这几个词，构造时直接报错，要求「描述工作本身，而不是怎么衡量它」。
  2. 运行记录里没有分数字段。RunView 的注释就一句：Never carries a score。打分函数 score() 只能由 core/judge.py 调用，并且只在选择落定之后。
  3. 评分痕迹绊线。任何 harness 文件的名字或内容里出现 "pass_rate"、deterministic_eval_result 这类评测输出特征，直接拒收，不能进经验库；基准还可以声明 leak_globs，把参考答案文件挡在证据之外。
  4. 匿名盲选。最终候选被打乱后编号成 A、B、C…，选择者不知道哪个出自哪种编辑。打乱用的种子由任务 ID、k 和模式算出，重跑结果完全一致。

harness2/core/spec.py · BenchPrompts节选

for bad in ("benchmark", "evaluation", "grader", "rubric", "score"):
    if bad in low:
        raise ValueError(
            f"BenchPrompts.{field_name} must describe the WORK, not its "
            f"measurement (found {bad!r}). Say what the practitioner needs."
        )

改坏了怎么办

编辑模型交回的 harness 要过三关：文件必须在八类组件范围内，结构要合法（比如技能要能被触发），还要过基准自己的校验。不通过就把报错原样塞回去让它再改一次（STAGE_ATTEMPTS = 2）。还是不行，这个阶段就退回当前的 harness 继续往下走，整个流程不会断。

所以这里的报错信息是写给模型看的，读起来像操作指南。BenchmarkAdapter.validate_tree 的文档要求「用可执行的语言列出所有问题，这段话会原样作为重试反馈」。

经验库：存整棵树，不存摘要

每个任务结束后，反思步骤会逐条说明每个编辑起了什么作用，再提炼成四个字段：线索（什么情况下适用）、教训、证据、置信度。如果运行之间看不出能复用的差别，就只写一行 NO_ENTRY，不硬凑经验。

经验库按领域分目录，每条记录保存完整的 harness 文件树和一份 EXPERIENCE.md。library.py 的注释说得很直接：「携带整棵树，从不只存摘要」。同领域的下一个任务开始提议时，就能翻阅前面所有被采纳的方案。

和上一篇的联系

编辑模型除了走 OpenCode，还可以走 claude_cli 通道：proposer.py 直接以 claude --dangerously-skip-permissions -p --output-format json 调用 Claude Code。它判断失败时同时检查 is_error 和 subtype，正是我们在 Claude Code 实验一里看到的那两个独立字段。

安全提示

README 明确写着：执行器网络不受限，Codex 运行时关闭沙箱；走 claude_cli 通道时，编辑模型也跳过了权限确认。跑真实基准前应该放在隔离环境里，并按文档限制网络，免得 Agent 直接上网搜到公开的评分标准。

04复现：跑通官方离线演示

仓库自带 harness2-demo：用脚本代替编辑模型和选择模型，但递归流程、预算记账、经验库全是真代码，执行也是真的 Python 进程，不需要任何模型账号。

演示任务是对账：把 CSV 里带正负号的金额加起来。基础 harness 里埋了一个 bug：

harness2/demo.py · 基础 harness 的 scripts/summarize.py节选

total = sum((amount for amount in amounts if amount > 0), Decimal(0))   # 只加了正数，漏掉了支出

脚本化的编辑者会把 if amount > 0 删掉，看框架能不能把这个改动探测出来、选中，再写进经验库。

实验环境

Windows 11，Python 3.12.14，harness2 @ 1cfe254，--k 2，并行和串行两种模式都跑。官方只支持 Linux，所以下面先踩了两个坑。

坑一：fcntl 是 Linux 专属

第一次运行，两个任务都报 ModuleNotFoundError: No module named 'fcntl'。全仓库只有 schedule.py 用它给汇总文件加跨进程锁。演示是单进程，用一个什么都不做的同名替身顶上即可。

坑二：Windows 路径分隔符让所有改动被静默丢弃

换上替身后，流程跑完了，但所有候选的答案都还是错的 Total: 105.25，最后脚本选择者在候选里找不到正确答案，抛了 StopIteration。

挂上调试钩子一看，每个编辑阶段都退回了原始 harness，报错是：

these files are off the editable surface and were not applied:
plugin\README.md, scripts\README.md, skills\README.md, sub_agents\README.md

根源在 core/tree.py 第 140 行：rel = str(p.relative_to(d))。Windows 上得到的是 scripts\summarize.py，和框架期望的 scripts/summarize.py 对不上，于是整份编辑被判定为「越界」而拒收。框架的兜底机制让它不会崩溃，只会悄悄退回原样，所以光看「2 个任务完成」根本发现不了问题。

修法是一行：把 str(p.relative_to(d)) 换成 p.relative_to(d).as_posix()（第 167 行同理）。为了不改仓库源码，我写了一个启动脚本在运行时打上这两处补丁：

run_demo_win.py完整代码

import inspect, sys
from harness2.core import tree

src = inspect.getsource(tree)
fixed = src.replace("str(p.relative_to(d))", "p.relative_to(d).as_posix()").replace(
    "str(p.relative_to(dest))", "p.relative_to(dest).as_posix()"
)
assert fixed.count(".as_posix()") == 2   # 上游改了就报错，提醒重新核对
exec(compile(fixed, tree.__file__, "exec"), tree.__dict__)

from harness2.cli.demo import main
sys.exit(main())
# 同目录再放一个 fcntl.py：定义 LOCK_EX、LOCK_UN 和一个空的 flock()
PYTHONPATH="shim;." python3.12 shim/run_demo_win.py --output runs/demo --k 2

诚实说明

演示里的编辑者和选择者都是写死的脚本：选择者会自己把 CSV 加一遍，再挑答案对的候选，这相当于看了标准答案。真实运行时这一步由模型完成，看不到正确答案。所以这个演示证明的是流程和管线能跑通，不能证明效果。效果要看论文和真实基准。

05结论

ONE-LINER

Harness² 把「调 Agent 的提示词和工具」变成一个有预算、有对照、不看答案的自动实验：分两个方向各改一版，在同一任务上真跑一遍比差别，合成后盲选，再把经验按领域存下来留给下一个任务。

适合谁

  • 在做 Agent 产品、想系统化地迭代提示词、技能、脚本的人
  • 研究「不训练模型也能提升 Agent」的人：代码和论文配套，流程完整
  • 想学怎么设计防作弊评测流程的人：四道防线很值得抄

什么时候不该用

  • 只想要一个开箱即用的 Agent：它是改进框架，不是 Agent 本身
  • 预算紧张：每个任务 4k 次完整运行加 3k 次编辑调用，真实基准下成本不低
  • Windows 本地开发：官方不支持，至少要处理本文的两个坑，最好用 Linux 或 WSL

猪猪的三条收获

  1. 把「怎么做」和「懂什么」拆开改。INV 和 DOM 两种编辑互不越界，合成时再取长补短。自己调提示词时，也可以把流程问题和领域知识分开迭代。
  2. 兜底机制会掩盖 bug。改动失败时「退回原样继续跑」让系统很稳，但也让 Windows 路径问题完全静默，任务照样显示完成。有兜底的地方，一定要把「兜了几次」也统计出来。
  3. 评测要从结构上防泄漏。不靠「请不要看答案」的提示，而是让数据结构里根本没有分数字段，打分只在选择之后，再加上关键词绊线。
